# Agent 生产治理

第 10 条企业级路线把已有运行统计升级为可以真正保护生产环境的规则。它不改变任务、工时或结算数据，只约束 Agent 如何回答、何时切换模型以及新版本如何上线。

## 用户能得到什么

- 主模型不再因为一次超时或一次格式错误就被替换。系统先使用同一个模型重试，只有连续超时、额度限制、供应商故障、鉴权故障、连续无效结果或能力明确不匹配时才允许启动应急模型。
- 每次回退都会记录主模型、故障类别、尝试次数和时间。用户取消、只失败一次或原因不明时，系统禁止自动回退。
- 设置页“运行与质量中心”直接显示回答成功率、事实验真率、P95 响应时间、主模型完成率和后台任务稳定性，不需要管理员自己解读零散指标。
- 指标突破红线时发布状态变为“已阻止发布”，避免明知系统不稳定仍继续上线。
- 新版本不再立即接管全部流量。发布器先上传独立候选版本，用版本定向请求核对健康接口、事实协议、版本号和前端资源；全部通过后才推广到 100%。
- 候选验证失败时，Cloudflare HTTP API 会立即把 100% 流量恢复到上一稳定版本。全流程永久不使用 Wrangler。

## SLO 红线

| 目标 | 默认标准 | 作用 |
| --- | --- | --- |
| 回答成功率 | 至少 99% | 约束 Agent 整体可用性 |
| 事实验真率 | 100% | 防止金额、工时、任务状态等未经工具核对就进入答案 |
| P95 响应时间 | 不超过 45 秒 | 防止少量快请求掩盖普遍卡顿 |
| 主模型完成率 | 至少 99% | 备用模型只能处理极端故障 |
| 后台任务失败率 | 不超过 1% | 约束附件分析和深度任务稳定性 |

样本少于 20 条时显示“正在积累样本”，不会把偶然的一次失败误判为长期事故；候选版本仍必须通过发布冒烟检查。

## 受控发布与回滚

1. 构建并上传静态资源和 Worker 候选版本，但不直接替换稳定版本。
2. 保留上一版本 99.99% 流量，候选版本仅占 0.01%，并使用 `Cloudflare-Workers-Version-Overrides` 定向验证候选版本。
3. 核对 `/api/health`、结构化事实协议、应用版本号、入口资源哈希和资源可访问性。
4. 全部通过后把候选版本提升到 100%。
5. 任一检查失败时自动把上一版本恢复为 100%，发布命令以失败退出，阻止 GitHub 版本闭环。

Cloudflare 版本回滚只恢复代码和静态资源，不回滚 D1/R2 数据。因此数据库迁移仍必须保持向后兼容，涉及破坏性数据变化时不能依赖代码回滚替代数据方案。

## 外部运行告警

可通过 `GOVERNANCE_WEBHOOK_URL` 和 `GOVERNANCE_WEBHOOK_SECRET` 接入企业告警系统。应急模型启动时发送签名事件，接收方使用 `x-giverny-signature` 验证 HMAC-SHA256。

事件只包含版本、模型、请求类型、故障类别、尝试次数和时间，不包含用户问题、模型回答、任务名称、附件、金额或其他业务正文。未同时配置地址和签名密钥时不会向外发送。

这条运行告警连接器与“沟通 Agent”不同：它用于系统故障通知，不代表 Agent 已经可以代替用户发送业务邮件、飞书消息或日历邀请。
